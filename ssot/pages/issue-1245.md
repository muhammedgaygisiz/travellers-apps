- [security: Places API requests are 100% unverified in App Check monitoring](https://github.com/muhammedgaygisiz/travellers-apps/issues/1245) (Issue \#1245)
- Description
  - iOS release-candidate Run 4 for [issue 1176](https://github.com/muhammedgaygisiz/travellers-apps/issues/1176) on TestFlight 1.0.1 build 91 found the Firebase Console App Check page reporting Storage 98% verified, Cloud Firestore 100%, and Authentication 96%, while the Google Maps Platform section reported Places API (New) at 0% verified and 100% unverified in Monitoring.
  - Restaurant, city, and Bite place search worked throughout the run, so production Places traffic was real but attributed to no verified client. Enforcement could not be considered while store-distributed traffic looked exactly like unauthorized traffic.
- Finding
  - The request path is the same on iOS, Android, and web, and it is not a client path. The app calls the `searchPlaces`, `searchNearbyPlaces`, and `getPlaceDetails` callables through `@capacitor-firebase/functions`; the Cloud Functions then call `places.googleapis.com` server-to-server with `X-Goog-Api-Key` and a minimal field mask.
  - No app, library, or native project reaches a Google Maps host, and neither the iOS Podfile nor the Android build file links a Maps or Places SDK. There is exactly one Places request path, and it starts in the backend.
  - Google Maps Platform App Check only accepts tokens minted by the client Maps and Places SDKs. A server-to-server REST call has no App Check token to attach, so 0% verified is the correct reading of this architecture rather than a regression or a misconfiguration. The dashboard is reporting the absence of a client integration, not the absence of protection.
  - Enabling App Check enforcement on Places API (New) would therefore reject 100% of BiteTribe's legitimate Places traffic and break restaurant, city, and Bite place search. It must stay in Monitoring for as long as Places is reached from the backend.
- Decisions
  - The verified control for Places sits one step earlier, on the callable. `searchPlaces`, `searchNearbyPlaces`, and `getPlaceDetails` are registered through `onAppCheck`, so App Check is enforced everywhere except the Functions emulator, and each rejects a request without `request.auth`. Every Places request Google sees was preceded by an App Check verified, signed-in call - the same attestation Run 4 evidenced at 100% on Firestore.
  - This is stated as the equivalent control rather than implying App Check covers Places. The Console will keep showing 0% verified, and that number is now documented as expected instead of being read as an open gap on every release run.
  - The key stays backend-only. It is bound as a Firebase secret (`GOOGLE_GEOCODING_API_KEY`) and never shipped to a client, so an application restriction by bundle id or referrer does not apply to it. Its protection is API restriction plus the callable boundary.
  - A native Places SDK would support App Check directly and would move the boundary back to the client. That is a deliberate future decision - more App Check surface, but the API key would then live in the distributed artifact and Places would be callable without a signed-in user. It is not adopted here, and the guard spec fails if one is linked without revisiting this page.
  - The reasoning is only durable if the request path cannot drift, so both halves of it are pinned by tests rather than by prose: no client may reach a Google Maps host, and no callable may be registered without App Check enforcement.
- Outcome
  - `src/__specs__/google-maps-request-path.spec.ts` scans every app and library source for Google Maps hosts and fails when one appears outside the functions backend, fails when the iOS or Android project links a Maps or Places SDK, and fails when any callable is registered without `enforceAppCheck: true` or the emulator-aware `getAppCheckCallableOptions()`.
  - The Places callables gained boundary coverage: registration through `onAppCheck`, rejection of unauthenticated text, nearby, and details requests, rejection of a missing position and a blank place id, the short-search-text early return that never reaches Google, and the backend-only key travelling in `X-Goog-Api-Key` rather than to the caller.
  - `libs/bite-tribe/api/.../__specs__/search-places.spec.ts` pins the client side of the same contract: all three place lookups go through `FirebaseFunctions.callByName`, which is what attaches the App Check token, and each degrades to an empty result instead of a hard failure.
  - [[Architecture - Firebase]] and [[Implementation - Firebase Functions]] record the Google Maps Platform boundary and the API-key restriction requirement.
- Remaining console and device work
  - Restrict the `GOOGLE_GEOCODING_API_KEY` key in Google Cloud Console to Places API (New) and Geocoding API only, with no application restriction. Cloud Functions egress addresses are not stable without a VPC connector and Cloud NAT, so an IP restriction is not usable as things stand.
  - Leave Places API (New) in Monitoring. Do not enable App Check enforcement for it.
  - Record the resulting dashboard state on the next physical TestFlight run under [[Current State - Release Candidate Test Charter]]: Places still at 0% verified is the expected outcome, and the evidence to capture is that place search works while the Firebase APIs remain enforced.
  - Android and web place search remain unverified on real artifacts and stay explicit under [[Current State - Known Issues]].
- Validation
  - `npx nx test bite-tribe/api --testPathPatterns=search-places` - 7 tests green.
  - `npx jest --config jest.config.cjs src/__specs__/google-maps-request-path.spec.ts` from `apps/bite-tribe-firebase/functions` - 5 tests green, and both guards were confirmed to fail against a deliberately introduced client-side Places host and an unenforced callable.
  - `npx jest --config jest.config.cjs src/functions/restaurants` from `apps/bite-tribe-firebase/functions` - 47 tests green.
  - Not run: a physical TestFlight pass, which is the console evidence listed above and cannot be produced from the repository.

- [epic: QR table menu and table ordering](https://github.com/muhammedgaygisiz/travellers-apps/issues/1072) (Issue \#1072)
- Description
  - \# Epic: QR table menu and table ordering
  - Part of \#735 (stage 3).
  - A guest at a table scans a BiteTribe QR code, sees the right menu for the right table, and places an order.
  - \#\# Goal
  - After scanning, the guest gets an unambiguous confirmation such as "You are ordering at Sakura Kitchen, table 12", browses the menu, and submits an order that reaches the restaurant attached to the correct table.
  - \#\# Scope
  - Stable menu item identity and availability, a prerequisite for order lines
  - QR token resolution and backend validation
  - Guest table sessions, including joining an existing session
  - Public menu browsing without a BiteTribe account
  - Cart and order submission
  - Order status and follow-up ordering
  - Staff-facing incoming order queue
  - Request staff assistance and request the bill
  - QR abuse protection
  - Offline tolerance and idempotent submission
  - \#\# Validation the backend must perform on every scan
  - The restaurant exists and is active
  - Table ordering is enabled for that restaurant
  - The table exists, belongs to that restaurant, and is enabled
  - The QR token is valid, active, and not revoked
  - The restaurant is currently accepting orders
  - The requested menu exists and is available
  - A QR code identifies a table context. It does not prove the guest is physically present. Treat presence as unproven and design the operational flow so a remote scan cannot cause harm beyond a rejected or staff-visible pending session.
  - \#\# Menu item identity problem
  - `MenuItem` in `libs/bite-tribe-common/model/src/lib/menu.ts` has no id. Items are array entries inside `Menu.categories[]`, addressable only by name and array index. An order line cannot reference that safely: renaming or reordering a category would silently repoint historic orders.
  - Stable ids plus a price snapshot on the order line are therefore the first child issue of this epic and a prerequisite for everything else in it.
  - \#\# Success criteria
  - Scanning a table QR resolves to exactly one restaurant, room, and table, confirmed on screen before any order can be placed.
  - A guest without a BiteTribe account can view the menu and place an order, if the restaurant allows it.
  - An order submitted twice because of a flaky network creates one order, not two.
  - Staff see a new order within seconds, attached to the correct table.
  - A revoked or rotated token stops working immediately.
  - Prices shown to the guest are the prices recorded on the order, even if the menu changes mid-session.
  - \#\# Product decisions to confirm
  - These block implementation of the specific children noted.
  - Can multiple guests join the same table session? Proposal: yes, shared session per table.
  - Is an order shared by the table or separated by guest? Proposal: shared table order with per-line attribution.
  - Can guests order without a BiteTribe account? Proposal: yes, via anonymous auth, upgradeable to a full account at Bite creation.
  - How are duplicate or fraudulent scans handled? Proposal: rate limit per token and per device, plus staff visibility of pending sessions.
  - Can a QR code be used from outside the restaurant? Proposal: sessions require an active table state set by staff, which bounds off-premise use.
  - When does a table session expire? Proposal: on visit close, or after a configurable idle timeout.
  - How are table changes handled after ordering? Proposal: staff move a visit between tables; orders follow the visit, not the table.
  - How are unavailable items communicated? Proposal: `isAvailable` already exists on `MenuItem`; surface it and block adding unavailable items.
  - How are cancelled or incorrect orders corrected? Proposal: staff-side cancellation with a reason, guest-visible.
  - How are staff notified about new orders? Proposal: in-app queue plus push, reusing the existing notification infrastructure.

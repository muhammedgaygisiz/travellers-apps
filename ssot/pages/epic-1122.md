- [epic: Entitlement foundation and Pro feature gating](https://github.com/muhammedgaygisiz/travellers-apps/issues/1122) (Issue \#1122)
- Description
  - \# Epic: Entitlement foundation and Pro feature gating
  - Part of \#1121 (stage 0).
  - Give BiteTribe a server-owned answer to "is this user Pro?" and a single enforcement path for it, so subscriptions and paid BiteTrails can be built on state that cannot be forged from the client.
  - \#\# Why this is first
  - `subscriptionTier` exists as an optional number on the public user document (`libs/bite-tribe-common/model/src/lib/public-user.ts`) and is only read by the profile and settings pages. Nothing enforces it anywhere.
  - `apps/bite-tribe-firebase/functions/src/functions/users/create-user-on-auth-create.ts` writes `subscriptionTier: 1` for every new account, so under the intended semantics every user is already Pro.
  - `apps/bite-tribe-firebase/firestore.rules` still allows every authenticated user to read and write every document, so the field is client-writable today. \#1078 fixes the rules, and this epic must not assume it has already landed.
  - Every gate in stages 2 and 3 reads this state. Building a paywall before the state is trustworthy means shipping a paywall the user can switch off.
  - \#\# Goal
  - A single server-owned entitlement decides Pro access. Cloud Functions and Firestore rules enforce it. The app reads it, gates UI on it, and can never grant it.
  - \#\# Scope
  - An entitlement model and the definitive Free and Pro capability matrix
  - A server-owned entitlement store plus auth custom claims, written only by the backend
  - Correcting the default tier for new accounts and deciding what happens to existing ones
  - Backend enforcement in the search and location callables
  - Client entitlement state, a route guard and a template gating primitive
  - A localized paywall screen and contextual upgrade prompts with Storybook coverage
  - Monetization funnel analytics events
  - Emulator rule tests covering allow and deny
  - \#\# Free and Pro capability matrix
  - | Capability | Free | Pro |
  - | --- | --- | --- |
  - | Home feed and map within 15 km of the current position | Yes | Yes |
  - | Client-side search and filtering inside the loaded 15 km set | Yes | Yes |
  - | Map zoom and zoom gestures | Yes | Yes |
  - | Creating, editing, liking, reviewing and saving Bites | Yes | Yes |
  - | Bucket lists and free BiteTrails | Yes | Yes |
  - | Backend search: `searchBites`, `searchBitesByCity`, `searchRestaurants`, `searchUsers` | No | Yes |
  - | Loading Bites at a position or city other than the current one | No | Yes |
  - | Radius beyond 15 km | No | Yes |
  - | Ads | Shown | Hidden |
  - \#\# Success criteria
  - A free account calling a Pro-only callable is refused by the backend, proven by a Functions test.
  - A user cannot grant themselves Pro by writing to their own user document, proven by an emulator rule deny test.
  - New accounts are created as Free, and the treatment of existing accounts is a recorded migration decision rather than a silent flip.
  - Reaching a Pro capability as a free user shows a paywall, never a broken or empty state.
  - The paywall is fully localized in every supported locale and has Storybook states.
  - \#\# Out of scope
  - Any purchase flow, store product or billing integration. Stage 2 owns that.
  - Paid BiteTrail content access. Stage 3 owns that.
  - A creator or business tier.
  - \#\# Product decisions to confirm
  - What happens to existing accounts that currently carry `subscriptionTier: 1`? Proposal: treat them as Free at cutover, because the value was never earned and pre-launch account volume is small. The alternative is a grandfathered Pro grant as a launch thank-you.
  - Should a free user see a locked preview of Pro results, for example a blurred count of matches in another city, or nothing at all? Proposal: a locked preview, because an empty state converts badly.
  - Does the entitlement claim need a forced refresh when a subscription lapses mid-session? Proposal: yes, force an ID token refresh on webhook-driven change.
  - \#\# Validation
  - Focused Nx targets for each touched project, Functions tests for every gated callable, and Firestore emulator rule tests with at least one allow and one deny case for the entitlement document.

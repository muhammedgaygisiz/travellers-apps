- [epic: publish operator-curated city landing pages so the product markets itself](https://github.com/muhammedgaygisiz/travellers-apps/issues/1487) (Issue \#1487)
- Description
  - \# Epic: publish operator-curated city landing pages so the product markets itself
  - BiteTribe holds data no food blog has: real dishes, real prices, real member photos, each already enriched with a city and a country. None of it is reachable by a search engine. The app is a single-page app behind a login, `robots.txt` disallows every authenticated surface, and `sitemap.xml` lists four URLs — the root, `/support`, `/privacy` and `/account-deletion`. A person searching for what to eat in a city has no way to arrive at BiteTribe, and the only public content the product emits is the site card and a share stub per Bite.
  - This epic gives an operator a way to turn the content the tribe already produced into public, indexable pages: a short curated list of three to five places in one city, server-rendered, reachable without a session, and linking into the app.
  - \#\# Why now, and why this shape
  - Issue \#894 built the reverse-geocoding enrichment that writes `city`, `region`, `country` and `countryCode` onto every Bite, and named "city pages" as one of the features it existed to enable. The data has been accumulating since. Nothing reads it for this purpose yet.
  - Issue \#1454 established the web metadata contract in [[Implementation - Web Search And Social Metadata]]: the canonical host, the static tags, `robots.txt`, `sitemap.xml`. It deliberately stopped at the four session-less routes, because there was no fifth. This epic adds the first family of public content the site has ever had, and it has to extend that contract rather than work around it.
  - `handleSharedLinkToBite` already proves the mechanism. It is a public `onRequest` at the `/s/**` rewrite that reads Firestore through the Admin SDK, sanitises field by field, and returns server-rendered HTML with Open Graph tags. A city page is the same shape at a different route with a bigger template.
  - \#\# Goal
  - An operator picks a city, writes a short introduction, chooses three to five places with a sentence about each, and publishes. The result is a page on `https://bitetribe.app` that a crawler can read in one request, that unfurls with its own card, that carries structured data, and that offers one clear path into the app.
  - \#\# Scope
  - \#\#\# Serve the page from a function, not from the app
  - A new `renderCityPage` `onRequest`, reached through an `/eat/**` rewrite on the `bite-tribe` hosting target. Route shape `/eat/<city>/<slug>`, for example `/eat/berlin/best-sushi`.
  - Server rendering is the decision, and it settles the access question rather than answering it separately. The page never opens a client Firestore connection, so App Check and the security rules are not in its path at all. The alternative — a public route in the Angular app reading Firestore from the browser — would need public read rules and an App Check exemption, and \#1078 has not yet replaced the open rules. Adding a second public read surface while that is outstanding is the wrong order.
  - Angular SSR is also rejected: there is no SSR anywhere in the workspace today, and the consumer app's bundle is the wrong payload for a document whose job is to be parsed by a crawler.
  - Caching carries the load. `Cache-Control: public, max-age=300, s-maxage=3600, stale-while-revalidate=86400` puts Hosting's CDN in front of the function, so per-view cost is negligible and a republish propagates within the hour.
  - \#\#\# Split the shared template, and depend on the escaping fix
  - `renderHtml` emits a `meta http-equiv="refresh"` redirect, which is correct for a share stub and wrong for a landing page: the landing page is the destination, not a waypoint. The template splits into an unfurl stub and a full document, in \#1489.
  - Scoping this epic also turned up a defect in the same helper. `escapeHtml` calls `String.prototype.replace` with string patterns, so it escapes only the **first** occurrence of each character, and a Bite name containing two of each is enough to break out of a meta tag and execute script on the BiteTribe origin. That was confirmed in a browser and it is **not** part of this epic: it is \#1488, filed on its own at `P0` because it is a defect in shipped code rather than future work. \#1488 has since fixed the helper - every pattern is a global regex, `&` first - so this epic can rely on `escapeHtml` escaping the whole string. The functions were deployed on 7 September 2026, so the hosted endpoint is closed.
  - This epic depends on \#1488 landing first. Nothing here should render operator-authored prose through the helper until it escapes every occurrence.
  - \#\#\# Curate and publish from the admin app
  - The curation surface belongs in `bite-tribe-admin` alongside the other operator surfaces, gated on the `admin` role the way \#1469 established and \#1472 hardened. It is not a business-app surface: a restaurant curating the list it appears on is a conflict, not a feature.
  - Publishing snapshots the chosen restaurants into the page document — name, address line, image, the operator's sentence — rather than joining live at render time. A renamed, delisted or deleted restaurant would otherwise silently break a page that Google has already indexed, with nothing to signal it happened.
  - \#\#\# Declare the page to search engines correctly
  - The canonical is `https://bitetribe.app/eat/...`, on the canonical host. `handleSharedLinkToBite` still builds its canonical from `bite-tribe.web.app`, which \#1454 recorded as a known wart; the new function does not inherit it.
  - The pages carry JSON-LD `ItemList` and `Restaurant` structured data, and their own Open Graph and Twitter tags. Structured data is what earns a rich result, and it is the difference between a page that ranks and one that merely exists.
  - `sitemap.xml` is a static file in `apps/bite-tribe/public`, so a growing set of published pages cannot live in it. A second sitemap is served by the function from the published set, and `robots.txt` gains a second `Sitemap:` line pointing at it. The static sitemap is left alone.
  - \#\#\# Give the page one measurable way into the app
  - A single call to action, with the page slug carried as a link parameter so the destination can attribute the visit. Firebase Dynamic Links is shut down, so nothing here is built on it. The App Store and Play QR codes from \#1453 are the natural companion on a page reached from a desktop.
  - \#\# Success criteria
  - An operator can create, preview, publish and unpublish a city page without leaving the admin app, and without a deploy.
  - A published page returns a complete HTML document, containing its title, description, structured data and all three to five entries, to a request carrying no session and no App Check token.
  - An unpublished or unknown slug returns 404, not an empty page.
  - The Firestore security rules and the App Check configuration are unchanged by this epic.
  - Google's Rich Results test parses a published page with no errors, and the page's canonical is on `bitetribe.app`.
  - The published set appears in the function-served sitemap, and `robots.txt` points at it.
  - A repeat request for the same page is served by the CDN rather than by a function invocation.
  - Deleting a restaurant that appears on a published page does not break the page.
  - Operator-authored text containing multiple angle brackets or ampersands renders as text.
  - \#\# Out of scope
  - **Generating the content.** Every page is curated by a person. Automatic generation from the Bite corpus is the obvious next step and is deliberately not this epic, because a page that no one read before publication is exactly the thing search engines now penalise.
  - **Angular SSR for the consumer app.** Rejected above, and a much larger change.
  - **Localised pages.** The app ships eleven locales. The first pages are written in one language, and `hreflang` arrives with the second, not before it.
  - **Analytics on the page.** See the product decisions: adding a tracker to a public marketing page pulls in a consent banner, and that decision is taken deliberately rather than by reflex.
  - **Restaurant-owned pages.** A restaurant editing its own public page belongs with the claim flow in \#1069 and \#1077.
  - **Moving the `bite-tribe.web.app` references.** Unchanged from \#1454: the verified app-links host and the redirect target have to move together with a Play Console update.
  - \#\# Product decisions to confirm
  - **Do the member photos on these pages have permission to be there?** Restaurant images are not Google Places photos — `get-place-details` deliberately keeps `photos` out of its field mask on cost grounds — so the Places caching and attribution terms do not apply. Member Bite photos are the open question: publishing one on a public marketing page is a different use from displaying it in-app to signed-in members, and the terms and the privacy policy have to actually permit it. Proposal: first pages use restaurant-supplied and operator-supplied imagery only, and member photos wait for an answer.
  - **Does a public marketing page need an Impressum?** The site's public surface is currently support, privacy and account deletion. Editorial content published in Germany under a company name generally carries an imprint obligation, and these pages are editorial. Proposal: confirm before the first page is public, not after.
  - **What is the content bar for publishing a page?** Only one production restaurant has a menu today. Three to five entries with no dishes behind them is a thin page, and a set of them is the pattern that damages a domain rather than growing it. Proposal: a page may be published only when each entry has a stated minimum of real Bites with photos, and the first release ships one city.
  - **Where does the page live in the URL space?** `/eat/<city>/<slug>` is the proposal. It is on the canonical host rather than a subdomain, because a subdomain splits the ranking signal for no gain. The word `eat` is a guess and is cheap to change now and expensive later.
  - **Does an unpublished page keep its URL?** Unpublishing a page that has been indexed leaves a 404 in Google's index for a while. Proposal: unpublish returns 410 rather than 404, so the removal is explicit.

- Notes
  - The epic exists because a product conversation asked whether BiteTribe could produce its own marketing. The answer that survived scrutiny was narrower than the question: operator-curated pages over data the product already has, not generated pages over data it wishes it had.
  - **The blocking constraint is content, not code.** The function and the template are small. Thin "best five in X" pages are precisely what recent search-quality and site-reputation guidance targets, and a set of them can cost the domain more than it earns. Only one production restaurant has a menu today. The first release ships one city, and a publish gate keeps the rest honest.
  - Three architectural options were considered and two rejected. **Angular SSR** - no SSR exists in the workspace, and the consumer bundle is the wrong payload for a crawler. **A public Angular route reading Firestore from the browser** - it needs public read rules and an App Check exemption while \#1078 is still outstanding, which is the wrong order. **A function-rendered document behind the Hosting CDN** was chosen: it keeps rules and App Check entirely out of the path, and `handleSharedLinkToBite` already proves the shape.
  - **Scoping this epic found a live stored XSS**, which is now \#1488 and is not part of it. `escapeHtml` in `render-html.ts` passes string patterns to `String.prototype.replace`, so it escapes the first occurrence of each character and no more. A Bite name carrying two of each is enough to close the `og:title` attribute, close the meta tag, and open a real script element. Confirmed by rendering the payload through the current helper and template in a browser: one script element, executed. Both `bitetribe.app` and `bite-tribe.web.app` serve the endpoint, so it runs on the origin that also serves the web app. Priority `P0` was taken as "selected for execution" with the release-candidate blocker consequence explicitly declined; the reasoning is a comment on \#1488. **Fixed:** \#1488 replaced the string patterns with global regexes and added `render-html.spec.ts`. The functions were deployed on 7 September 2026, so the hosted endpoint is closed, and the escaping this epic's template work inherits is now whole-string.
  - Two non-engineering questions gate the first publish rather than the first commit: whether member photos may appear on a public marketing page, and whether an editorial page published from Germany needs an Impressum. Both are cheap to answer now and expensive to answer after a page is indexed. They are on [[Current State - Open Questions]].
  - Priority is `P3`. The epic is real and the enabling data has been accumulating since \#894, but nothing in the launch path depends on it.

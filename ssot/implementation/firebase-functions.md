# Implementation - Firebase Functions

## Purpose

Firebase Functions implement backend-owned behavior for search, notifications, auth-driven user creation, aggregate maintenance, storage post-processing, and scheduled engagement.

## Location

```text
apps/bite-tribe-firebase/functions/src/functions
apps/bite-tribe-firebase/functions/src/index.ts
```

## Implementation Rules

- Put backend-owned query semantics in functions when the client should not duplicate filtering logic.
- Keep callable request and result shapes typed.
- Use `onAppCheck` from `callable-options.ts` for frontend callable functions so App Check enforcement is applied consistently. `onAppCheck` keeps enforcement enabled by default and disables it only when the Functions emulator sets `FUNCTIONS_EMULATOR=true`.
- Preserve client-safe fallback behavior where the UI expects empty lists instead of hard failures.
- Add structured logs for operationally important branches.
- Every operator action logs through `logOperatorAction` in `shared/operator-log.ts`, and nothing else writes the audit fields. Cloud Logging is the only record of what an operator did to an account or a Bite (epic [#1471]), so the fields have to be the same in every callable or the trail is only readable by whoever wrote the one you are looking at - which is what it had become across eight callables and three names for the actor. The helper reads the actor off the request, so call it after `requireAdmin`. `src/__specs__/operator-action-logging.spec.ts` fails the build when an operator callable does not use it, when a callable hand-rolls `callerUid`/`callerRoles`/`requestedBy`/`targetUid` as a key, or when `OPERATOR_ACTIONS` names a callable that no longer exists. A new operator callable adds its name to `OPERATOR_ACTIONS`; a read-only one is exempt only by being named in the spec, and `listUsersWithRoles` is the only one. The shape, the queries it answers and the retention window it depends on are in [Architecture - Auth](../architecture/auth.md). See issue [#1477].
- Export new functions from `src/index.ts`.
- Backend-only third-party API keys should live in the functions runtime environment; Bite address enrichment expects `GOOGLE_GEOCODING_API_KEY`.
- Use the `bite-tribe-firebase:firebase-set-geocoding-secret` Nx target to set the production Google Geocoding secret before deploying functions that bind it; the target prompts for the secret value at execution time and must not store the value in `project.json`.
- Google Maps Platform is reached only from here, never from an app. Google Maps Platform App Check only accepts tokens from the client Maps and Places SDKs, so a server-to-server call cannot carry one and Places API (New) reports 0% verified by design; enforcement stays off for it. The control that replaces it is the callable in front of the API - App Check enforced plus an authenticated caller - so a callable that spends the Maps key must reject a request without `request.auth`. Keep the key backend-only and restricted in Google Cloud Console to Places API (New) and Geocoding API, with no application restriction, because Cloud Functions egress addresses are not stable without a VPC connector and Cloud NAT. Field masks stay minimal: Places is billed per field SKU. `src/__specs__/google-maps-request-path.spec.ts` fails the build when a client source reaches a Google Maps host, when the iOS or Android project links a Maps or Places SDK, or when any callable is registered without `enforceAppCheck: true` or `...getAppCheckCallableOptions()`. Adopting a native Places SDK would move the boundary into the distributed artifact and has to be decided against [issue-1245](../records/issue-1245.md), not by deleting the failing assertion.
- Engagement notification copy is localized in the backend. A push notification is rendered by the OS before the app runs, so Transloco can never reach it; the catalog in `shared/i18n` is the backend equivalent of the app's locale files. Senders name a message key, never an English sentence, and `sendLocalizedNotification` resolves each recipient's language from `settings/{uid}.language`, groups the enabled tokens per language, and sends one multicast per language. An account without settings, with an unsupported language, or with a regional locale such as `de-CH` falls back to the base language and then to `en`; a notification in the wrong language still beats no notification. Adding a language to `SUPPORTED_LANGUAGES` without its catalog fails the build. See issue [#1200].
- Every notification trigger sends through `shared/utils/send-localized-notification.ts`. Localization, chunking, and invalid-token cleanup live there so a new trigger cannot quietly ship English or skip the cleanup contract.
- Engagement notifications that link into the app must carry the data their landing page needs. The weekly summary sends the `weekStart`/`weekEnd` bounds it counted so `loadWeeklyBites` can serve exactly that week; requests without a usable range fall back to the previous calendar week. Week bounds live in `shared/utils/week-bounds.ts` and must not be re-derived per function.
- Migration callables that can invoke paid APIs should operate on explicit records, such as a selected `biteId`, so operators can repeat the migration deliberately without broad accidental API usage.
- Every HTTP endpoint decides who may call it, and records the decision in `src/__specs__/callable-authorization.spec.ts`. A callable runs with admin credentials, so a Firestore rule constrains nothing it does and `if (!request.auth)` is a check that a caller exists, not a check that this caller may. The spec names each endpoint `operator`, `restaurantAuthority`, `staffAuthority`, `authenticated` or `public`, then fails when an operator endpoint does not call `requireAdmin` from `shared/roles.ts`, when an endpoint a consumer path depends on does, when a restaurant- or staff-authority endpoint does not reach its own shared guard, or when a new endpoint appears that nobody classified. Guard the operation, not only the documents: `verifyRestaurantCandidate` creates a Restaurant, seeds its Menu and links Bites to it, and accepted any BiteTribe account until issue [#1472]. Each operator callable carries a deny test per rejected caller - no session, no roles, `business` only - because an allow test passes just as happily with the guard deleted. `resyncBiteCounts` and `resyncFollowCounts` look like operator actions and are not endpoints at all: they are `onSchedule` jobs with no caller to authorize.
- A notification addressed to one app store passes `platform` to `sendLocalizedNotification`, which narrows the recipients to the installations whose `pushTokens` document records that platform. An installation without a recorded platform is left out rather than guessed at. `sendNewVersionNotification` is manual on purpose: nothing observable tells the backend when a TestFlight build or Play Console review went live, and the two stores clear at different times, so the operator announces one platform at a time from the business migrations page and gets the reach back as `tokenCount`/`userCount`. See issue [#1194].
- Copy that names something the catalog cannot carry - a country, a currency, a date - receives the resolved language as the second argument of `buildMessage` and localizes the value through ICU. `shared/utils/country-label.ts` renders a country badge as flag plus localized country name in one value, so a locale places the whole badge in its own word order and a code ICU cannot name still reads. Do not add 200 country names per locale to the catalog. See issue [#1212].
- The country badge notification is owned by the badge, not by the Bite. `addCountryCodeToUser` reports the country code only when it was genuinely new to the profile, and `enrichBiteAddressOnCreate` calls `notifyOnNewCountryBadge` with it; a later Bite in the same country stays silent. The badge award is wrapped on its own so a failing send cannot travel back up and mark the Bite's address as `failed`. The `countryCodes` backfill path reports nothing, because it reconstructs a history the user already lived through, and `createUserOnAuthCreate` seeds `countryCodes: []` so a new account's first Bite is an achievement rather than the never-ran-before signal. Followers are only told when the profile is `public`. See issue [#1212].
- Restaurant candidate verification must keep the state transition backend-owned: create the Restaurant, create the Menu, link candidate Bites, and mark the candidate verified in one transaction. See [UC - Verify Restaurant Candidate](../use-cases/uc-verify-restaurant-candidate.md).
- Candidate verification seeds the new Menu from the candidate Bites instead of creating an empty one. The Bite documents are read inside the same transaction, before any write, and mapped through `shared/utils/initial-menu.ts`: Bites of the same dish become one item, its price is the average of the positive prices users reported, items are ordered by Bite evidence and then by name, and everything lands in the single `Bites` category the operator can rename in the business edit-menu page. A candidate without usable Bite names still produces an empty menu, and a Bite deleted after clustering is skipped rather than failing the transaction and stranding the candidate in `pending`. See issue [#1003].
- Candidate verification must be idempotent for already verified or merged candidates and return the existing `verifiedRestaurantId` rather than creating duplicates.
- Trigger-maintained counters must handle every lifecycle path that can change the count. If the counted entity can be deleted, add a matching delete-side decrement trigger when the create path increments.
- Trigger-maintained Bite like aggregates must migrate old Bite documents that are missing `thumbup`, `drooling`, or `mindblown` by recomputing counts from the `likes` subcollection before using increment/decrement deltas.
- Trigger-maintained aggregates are eventually consistent, so a client that also writes the counted document optimistically must not render the aggregate alone. The reaction counter takes the higher of the Bite aggregate and the likes the client already loaded; see [Bite](../domain/bite.md) and issue [#1165].
- Trigger-maintained user follow aggregates (`followersCount`, `followingCount`) must migrate user documents that predate the aggregate by recomputing the count from the `followers`/`following` subcollection before applying increment/decrement deltas, so existing users are not corrupted by a blind increment. The scheduled `resyncFollowCounts` backfills and corrects drift for users that never receive a follow write, mirroring `resyncBiteCounts`.
- One-off aggregate migrations must not live in read callables. `loadLeaderboard` reads the persisted `meta/leaderboard` ranking and rebuilds it only when the document is missing; the `biteCount` aggregate is owned by `incrementBiteCountOnBiteCreate`/`decrementBiteCountOnBiteDelete` with the scheduled `resyncBiteCounts` as the drift and backfill safety net. A temporary backfill added to a read path has to be removed once it has run, so every request stops paying for a full users-collection scan. See issue [#905].
- A cascade delete removes children and references first, and the record every read path resolves through **last**. `deleteBiteAsOperator` deletes the Bite document after its likes, its reviews, its Storage objects and every stale id in `restaurantCandidates`, `bucketlists` and `biteTrails`, and `deleteAccountForUser` deletes the Firebase Auth account after the data it owned, for the same reason: a failure halfway then leaves a record that can still be found and retried rather than an orphaned data set nobody can reach. Non-existence is refused up front, before anything is touched, so a mistyped id is a clean `not-found` rather than a half-finished cascade. Note that a trigger-maintained aggregate corrects itself only once the document goes — `decrementBiteCountOnBiteDelete` runs after the delete, so a check for the new count immediately after the callable returns reads the old one. See issue [#1475].
- Firestore does not delete a subcollection with its parent, and a top-level collection keyed back to a parent does not go with it either. Anything cascading over a Bite has to take `/bites/{id}/likes/*` and the `/reviews` documents whose `biteId` points at it; the id is stored as the path-shaped string `/bites/{id}` by every review write, and the bare id is matched as well because that shape is invisible to the read path and would otherwise be left behind.
- The Functions project cannot reach a workspace library — its `tsconfig.json` carries no path mappings — so a helper it needs from `libs/` is repeated next to its caller and the two are changed together. `shared/roles.ts` repeats the role list and `delete-bite-as-operator.ts` repeats `storagePathFromDownloadUrl`. Adding a workspace import here does not fail locally in an obvious way; it fails the functions build.
- Restaurant ownership is written by `assignRestaurantOwner` and `revokeRestaurantOwner` in `restaurants/restaurant-ownership.ts`, never by a client and never as a custom claim. Both are operator-only, both take a required reason because Cloud Logging is the only record an ownership change leaves, and both do the read and the write in one transaction so two operators cannot both see a restaurant unowned and both write. The pair lives in one module because it is one invariant: assign refuses a restaurant that is held and names the current owner, revoke refuses one that is not, and each is the other's precondition - split across two files they could drift on what counts as owned. Assign is idempotent on a repeat of the same assignment, matching `verifyRestaurantCandidate`. The target account has to hold `business`, read from its Auth record because roles are custom claims and no Firestore query can answer it. Revoke deletes `ownerUserId`, `claimedAt` and `claimedAtTimestamp` rather than blanking them, so "missing means unclaimed" stays the only rule a reader needs. See issue [#1077].
- Restaurant **staff** is written by `addRestaurantStaff` and `removeRestaurantStaff` in `restaurants/restaurant-staff.ts`, with `listRestaurantStaff` reading it back. They are the first callables that are **not** operator-only and not open to every account: `requireAnyRole(request, 'business', 'admin')` admits the caller, and `requireRestaurantAuthority` then reads `Restaurant.ownerUserId` to decide which restaurants that reaches - every restaurant for an operator, by `RD-UR-6`, and only the held ones for a restaurant owner. The classification spec calls this class `restaurantAuthority` and fails an endpoint in it that reaches for `requireAdmin` instead. Each writes two things that must agree - the `staff` custom claim and `/restaurantStaff/{uid}` - which cannot share a transaction, so the order is fixed instead: a grant writes the association first and a removal drops the role first, and each undoes its first write if the second throws, keeping the invariant "the role never exists without the association". Neither reads a role from the payload, so neither can grant `admin` or `business`, and both refuse an account that holds one. Both log through `logOperatorAction`; `listRestaurantStaff` is exempt as a read. See issue [#1537].
- Table **QR tokens** are written by `issueTableQrTokens` and `rotateTableQrToken` in `restaurants/table-qr-tokens.ts`, and kept true by the `syncTableQrTokenOnTableWrite` trigger. They are `restaurantAuthority` callables like the staff ones and share the guard: `requireRestaurantAuthority` in `restaurants/restaurant-authority.ts`, extracted from `restaurant-staff.ts` when this became the second surface asking whether a caller may act on a restaurant. A second copy of that answer could drift on which field carries ownership and whether an operator is admitted, which is exactly what a reviewer cannot check by reading one file - so the two classification specs follow the guard one hop and assert that the extracted module is itself guarded by `requireAnyRole`. A token is 130 bits from `crypto.randomBytes` rendered in Crockford base32: uppercase alphanumeric, so a QR code encodes it in alphanumeric mode rather than byte mode, and without `I`, `L`, `O` or `U`, so a code read aloud during a support call has no confusable pair. The generator takes no argument, which is the acceptance criterion rather than an accident of the signature. Issuing is idempotent - a table already holding an active token keeps it - because the publish step of issue [#1088] and the sheet page of issue [#1087] both ask, and a second call that minted new tokens would invalidate every sheet already printed. Token and `qrTokenId` are written in one transaction: a table pointing at a token that was never written resolves to nothing, and a token nothing points at can never be rotated, because rotation finds the current token through the table. See issue [#1086].
- A token document is **never deleted**. Rotation marks the old one `superseded` and names its successor; deleting a table marks it `revoked`. A deleted document would be indistinguishable from a code that was never issued, and a guest scanning a sticker nobody peeled off a retired table needs "no longer valid" rather than silence. The same trigger mirrors `roomId`, `label` and `enabled` onto the active token, because a table keeps its token when it moves room or is renamed (issue [#1085]) and `/tableTokens` copies those fields to make a scan one read - a copy nothing maintains is wrong exactly when it matters. It runs on the callables' own `qrTokenId` write too and is a no-op there, since what they wrote already matches what it would write.
- A scanned code is turned into an ordering context by `resolveTableQrToken` in `restaurants/resolve-table-qr-token.ts`, the **only `public` callable that reads restaurant data** (issue [#1100]). A guest at a table has no BiteTribe account and may never want one, and the scan is what establishes which restaurant they would be signing in to, so an auth requirement would make the account a precondition of finding out whether the restaurant even takes orders. App Check is enforced through `onAppCheck` like every other endpoint. It writes nothing: starting or joining a session is `startTableSession` below, and that is where an unproven presence first costs the restaurant anything.
- The public `get` on `/tableTokens` does **not** make the callable redundant. That read gives a phone a restaurant id, a room id and a table label and deliberately nothing else; five of the six things a scan has to establish live in documents a guest may not read, and three of them change without the token being touched - an assignment is revoked, the kitchen pauses, the clock passes closing time. A client deciding for itself would decide from a stale copy and its own wall clock.
- The six checks run **in the order [UC - Order At The Table Through A QR Code](../use-cases/uc-order-at-the-table-through-a-qr-code.md) states**: the restaurant exists and is active, table ordering is enabled, the table is published and enabled, the token is active, the restaurant is accepting orders, the menu has something on it. Several are false at once often enough to matter - a retired table at a restaurant that closed for the season and let its assignment lapse fails three - and the guest gets one sentence, so which one is a decision rather than an accident of nesting. It runs outside-in, so the answer is the largest true thing. The token document is read first because it names the restaurant, but its _status_ is not judged until its own turn: telling a guest their code was replaced when the restaurant behind it no longer exists sends them looking for a newer sticker that is not there.
- Each refusal is a **returned value, not a thrown error**. `TableScanResult` is a discriminated union, and `TABLE_SCAN_REFUSAL_REASONS` in `restaurants/table-scan.ts` is the closed set of twelve reasons a client switches over, each paired with one of three next steps - ask staff, try later, or look at the table again. Callable error codes come from a fixed list of sixteen that says nothing about restaurants, so a distinct reason would have had to travel in a free-form `details` bag no type describes, and "something went wrong" at a table is a guest putting their phone away. The reason list exists twice, for the `rootDir` reason above; `src/__specs__/table-scan-parity.spec.ts` compares both copies, following `table-state-parity.spec.ts`. The drift it guards against is a reason the backend returns and the client has no sentence for, which renders as an empty refusal screen.
- "The restaurant is **active**" is not a field. A restaurant is active while a business account holds it: an order placed at a restaurant nobody holds lands in a queue no account can open, and `claimStatus: 'revoked'` is exactly a restaurant that used to be able to take one. `assignRestaurantOwner` and `revokeRestaurantOwner` already write that fact, so the check reads it rather than a copy of it, and no backfill is needed.
- "The restaurant is **currently accepting orders**" is two things. `Restaurant.tableOrdering.pausedUntilTimestamp` is the staff-side stop - the kitchen is swamped, the terminal is down - and it is an _end_ rather than a flag, so the worst case is a restaurant that resumes by itself instead of one that never does. The other is the opening hours, evaluated by `shared/utils/opening-hours.ts` in `tableOrdering.timeZone`. Cloud Functions run in UTC and `DaySchedule` carries no zone, so without it a Jakarta restaurant would close at four in the afternoon; a range whose end is before its start runs past midnight, which is the case the module exists for. A schedule that cannot be evaluated - none stored, or a zone the runtime does not know - is treated as **open**, because `enabled` and the pause are the deliberate switches and a field nobody filled in is not one.
- The response is assembled **field by field** and is never a spread of the documents it was read from. `/restaurants/{id}` carries `ownerUserId` and the table document carries floor-plan geometry; the acceptance criterion is that a guest sees neither, and the only way to keep that true as those documents grow is for nothing in the answer to be a spread.
- Resolution costs **at most five reads** - token, restaurant, table, then room and menu in one `getAll` - and fewer on every refusal, because each check is reached only once the one before it passed. It runs on every scan of every table, including the scans that are somebody's script.
- Rate limiting is **two counters, cheapest first** (`RD-TS-24`). `shared/utils/scan-rate-limit.ts` is the first: two fixed windows per minute, one per token and one per client, counted **in the function instance's own memory**, costing no reads and no writes. It stops a loop against a warm instance and not a distributed one, because Cloud Functions scales out and each instance starts at zero. The two limits catch different things - the per-token one is somebody working on one table, the per-client one is somebody working through many tokens, which spends one request each and would never trip a per-token count. The client bucket is the caller's uid or the request IP, and deliberately **not** the App Check app id, which every install of the consumer app shares.
- `shared/utils/durable-scan-rate-limit.ts` is the second, added by issue [#1107], and counts in Firestore so every instance adds to one number. It runs on what the memory counter admitted, which is the whole cost argument: a flood against one warm instance is absorbed for free after the thirtieth request, and only traffic spread thinly enough to look ordinary to each instance reaches counters that cost something. Its limits are therefore **higher** than the per-instance ones rather than a second opinion on the same requests. It adds a third dimension, the IP, because `clientOf` answers the uid **or** the address - so an attacker holding one throwaway anonymous account per request was bucketed by neither, and anonymous accounts are free and unlimited by `RD-TS-4`. That dimension is a **cost raiser and not a boundary**, because `X-Forwarded-For` reaches `req.ip`; the address is hashed and truncated, and the token and the uid are not, because both are already stored in documents that outlive a counter by months and an IP appears in no other document in this product. A Firestore failure **admits** the scan: a limiter that cannot reach its counters and therefore refuses every guest in the product is a worse outage than the one it was reacting to.
- Both counters report the request that **crosses** a limit, not merely the ones past it, and that is what makes the throttling observable without making the report grow with the attack. The crossing reads the token document and raises a `rateLimited` row through `restaurants/record-scan-anomaly.ts`; the thousandth request after it reads nothing and writes nothing. Anomalies are also raised from two refusal paths in `resolveScan` - a table out of service, a restaurant that is shut - and from two things `startTableSession` observes **after** it commits: more live sessions on a table than it can seat, and a consented coarse position far from the restaurant. The writer is bounded a second time by `SCAN_ANOMALY_QUIET_MS`, so `ScanAnomaly.count` counts raisings and not requests. None of it can change what the caller got: `recordScanAnomaly` answers rather than throwing, because a guest whose session failed to start because a row on a staff screen could not be written would be the protection breaking the thing it protects.
- The optional `position` on `startTableSession` is compared to `Restaurant.position` and **discarded** (`RD-TS-27`). Only a rounded distance survives, on the rows far enough away to be worth one, and it gates nothing: a malformed position is dropped exactly as an absent one is, because the field is optional and sending a bad one must cost a guest no more than sending none.
- `rotateTableQrTokens` (issue [#1107]) replaces the codes of a room or of a named set of tables. It refuses a call naming neither, because "rotate every code in the building" must not be what a caller gets by leaving an argument out, and it runs one transaction per table rather than one over the room: a table's token document and its `qrTokenId` still have to land together, but an all-or-nothing guarantee over a whole room cannot honestly be had at that size, and an owner whose run failed at table 19 of 24 is better served by 18 rotated tables and an error than by nothing. It is `restaurantAuthority` like the single rotation, and deliberately **not** the `staffAuthority` that `dismissScanAnomaly` takes: clearing a row is reading it, and replacing a code is a trip to the printer (`RD-TS-28`).
- **A guest's attachment to a table** is written by `startTableSession` and `leaveTableSession` in `restaurants/start-table-session.ts` and `restaurants/leave-table-session.ts` (issue [#1101]), and by `transitionTableState` below. They are the only two callables an **anonymous** session may reach, and that is the decision rather than an oversight: a session has to belong to somebody, or the guest's phone could not read it back through the rules and `linkWith*` could not later turn it into an account without the session changing hands. What the door opens onto is one document named `{length}_{tableId}_{uid}` - neither callable takes a `guestUserId`, so a caller can only ever address its own, and the restaurant, table and visit all come from a token it had to hold. `startTableSession` re-runs the twelve checks of issue [#1100] through the shared `resolveScan`, because the resolution the client is holding is as old as the time the guest spent reading the confirmation screen.
- **A scan does not occupy the table** (`RD-TS-1`). With no open visit at the table, the session is written `pending`, which cannot order, and no `tableStates` document is touched at all - so a code scanned from a photograph costs the restaurant one row on a screen rather than a table the next party cannot be given. With a visit already open the guest is `active` immediately, because staff have confirmed that a party is at that table and which of them is holding the phone is not a question worth asking. The join follows `TableState.visitId` and nothing else, which is also what makes "a guest cannot join a closed visit" true rather than checked: ending the visit dropped the pointer.
- **Sessions are idempotent by document name.** `{length}_{tableId}_{uid}` is derived on both the client and the backend, so one phone scanning one code twice addresses one document, keeping its `startedAt` and gaining the visit if the table has been seated since. The leading length is what makes the derivation injective - with a plain separator, `table_` with `guest` and `table` with `_guest` name one document and two guests would share a session. `src/__specs__/table-session-parity.spec.ts` pins the spelling, because nothing compares the two derivations at runtime: a separator changed on one side leaves a guest watching a document nothing ever writes, with both codebases passing their own tests.
- **Expiry is a predicate, not a job.** `isExpiredSession` is read against the restaurant's `tableOrdering.sessionIdleTimeoutMinutes`, defaulting to two hours, and whichever callable next observes an expired session persists the status. Nothing is scheduled, because a session nobody touches costs nothing and matters to nobody; the moment expiry matters is the moment somebody asks.
- **A restaurant's menu is read without an account** by `loadPublicMenu` in `menus/load-public-menu.ts` (issue [#1102]), the second `public` callable. It takes a `restaurantId` rather than a token, because the entry point it exists for is a link a restaurant publishes and such a restaurant may have no floor plan and no printed codes at all. It assembles the restaurant _and_ the menu field by field - the restaurant document carries ownership and ordering configuration a reader is not entitled to - and passes the menu through `backfillMenuIds` without persisting the result, because a public read has no business writing to a restaurant's menu. Its four refusals are all about there being nothing to read; none is about ordering, and `menuEmpty` is deliberately weaker than the scan's `menuUnavailable`, because a menu whose every dish is off cannot be ordered from and is still worth reading.
- **An order is written by `submitTableOrder`** in `restaurants/submit-table-order.ts` (issue [#1103]), the third callable an **anonymous** session may reach and, like the other two, one that takes no `guestUserId`: the session it addresses is named after the caller's own uid, the visit comes off that session, the table comes off that visit, and every price comes off the restaurant's own menu. There is nothing in the request a caller could choose that would reach another party's dinner. Everything is read inside one transaction, because a meal sits between the scan and the tap: the kitchen can pause, the owner can reprice a dish, a member of staff can close the visit, and the party can be walked to another table.
- **The prices are checked, not taken** (`RD-TS-10`). The phone sends the unit price it displayed on every line as a _claim_; the callable compares each to the live menu and refuses the whole order on the first difference, naming the item and both prices. Snapshotting whatever the menu says would silently recharge a guest whose dish was repriced while they read its description, and trusting the client's number would let a client name its own price - so what is written is always the menu's number, and only when the two agree. Availability travels down the same way `isMenuVariantAvailable` says it does, and a variant is reached **through** the dish it belongs to, so a client naming the large Margherita as a variant of the tiramisu finds nothing.
- **The order's table comes off the visit, never off the session.** `moveTableVisit` does not touch sessions, so a party walked to a bigger table keeps a session that goes on naming the table its guest scanned. Reading the table off the session would record the order against a table the party left and move a table nobody is sitting at.
- **A menu that states no currency cannot be ordered from.** `Menu.currency` is optional and absent means "not stated" rather than a default (issue [#1102]), which is right for a menu somebody is reading and impossible for one somebody is ordering from: `OrderLineSnapshot` requires a currency, and the alternative to the `menuCurrencyMissing` refusal is guessing one and printing it on a receipt.
- **The guest's order moves the table, and this callable writes that move** (`RD-TS-11`). `transitionTableState` is guarded by `requireTableStateAuthority`, which a guest cannot pass and which must not be widened - it would hand the floor's state machine to anybody holding a photographed QR code. So the `occupied -> ordering` change is written here, in the same transaction as the order, from the same `TableState` and `TableStateTransition` types and against the same `canTransitionTableStatus` matrix; the shared **types** are the drift protection, because a field added to either is a compile error in both places. A table already `ordering` is left alone, since refusing that would refuse every round after the first. The audit entry names the guest and carries no roles.
- **The order status lifecycle is data, in both copies.** `restaurants/table-order.ts` repeats the five statuses, the end set, the transition matrix, the refusal reasons and `tableOrderTotal` from `libs/bite-tribe-common/model`, and `src/__specs__/table-order-parity.spec.ts` compares all five as text. Three of them drift silently: a refusal reason the client has no sentence for is a blank line in front of a guest who cannot order; a matrix row the staff queue of issue [#1105] believes is legal is a button that does nothing; and two copies of the total are the guest agreeing to one figure and the restaurant recording another.
- **Sending twice makes one order** (issue [#1108]). The optional `requestId` argument names the order document - `visits/{visitId}/orders/req-{requestId}` - so deduplication is a read of one document rather than a search for an order that looks similar, and the read is inside the transaction so two copies of one request contend on it: the loser's read set is touched by the winner's `create`, Firestore retries it, and the retry finds the order and answers with it. The existing order is returned **before** the session status, the visit, the table status and the lines are checked, because a replay arrives after the world has moved on and none of that makes the order that already landed untrue; the answer carries `replayed: true`, since the two are the same outcome and not the same event. The key's spelling is issue [#1096]'s, and `table-order-parity.spec.ts` compares the prefix, the pattern and the derivation across both copies - a second spelling would make a landed order invisible to the phone that sent it. The argument is **optional**, so every client written before the issue goes on working.
- **A refused scan now means there is nothing to show.** `TABLE_SCAN_REFUSAL_REASONS` is ten and was twelve (issue [#1102]): `tableOrderingDisabled` and `orderingPaused` became `TableOrderingAvailability`, carried on a scan that resolved, so a menu-only restaurant resolves exactly like an ordering one and differs in one field. `startTableSession` refuses such a scan even so - a session exists in order to place orders, and one at a restaurant that takes none can never be used.
- **Live table state** is written by `transitionTableState` in `restaurants/transition-table-state.ts`, and by nothing else - `firestore.rules` refuses every client write to `/restaurants/{id}/tableStates` and `/restaurants/{id}/tableStateTransitions`, so the callable is the only path rather than the path the app happens to take. The reason is the race: two hosts tapping "seat" on table 12 in the same second would, with client writes, produce one table, two parties and no record. The callable takes the status the caller **believes** the table holds, reads and checks it inside a transaction, and writes the new state and one append-only audit entry in the same commit. Firestore retries the transaction whose reads were touched, so the loser re-reads the winner's state and is refused `aborted` with the current status, who set it and when - which is what lets the UI say "someone else just seated this table" instead of "failed". Requiring the expected status rather than accepting it is the whole difference: without it the loser is refused for attempting `occupied` to `occupied`, a remark about the matrix rather than about the conflict. See issue [#1092].
- It is classified `staffAuthority`, a fourth class and the first a `staff` account may enter. `requireTableStateAuthority` in `restaurants/restaurant-authority.ts` admits `staff`, `business` or `admin` and then reaches its restaurant through `Restaurant.ownerUserId` for the last two and through `/restaurantStaff/{uid}` for the first - the same pair `worksAt()` checks in the rules, never the `staff` role alone, which would make the role a key to every dining room in BiteTribe. It is deliberately **not** `requireRestaurantAuthority` with a wider role list: that one answers "may you configure this restaurant", which staff must never pass, and this one answers "may you operate it during service", which is all staff may do. One function taking a role list would put the difference in an argument at each call site, and the call site that got it wrong would be the one handing a host the QR rotation.
- It is deliberately **not** in the operator trail. `logOperatorAction` records privileged one-off actions to Cloud Logging for an operator who goes looking; a seating happens a few hundred times a service, its audience is the restaurant, and what it needs is a record the business app can show beside the table. That record is `tableStateTransitions` - durable, queryable, scoped to the restaurant that owns it, and append-only because a disputed table is answered by a history nobody could have edited. A second thinner copy in the operator trail would bury every real operator action in seating traffic. `operator-action-logging.spec.ts` does not claim it, because the callable reaches its own guard rather than `requireAnyRole` or `requireRestaurantAuthority` directly.
- **Table visits** are opened and ended by the same callable, because seating a table _is_ opening a visit and freeing it _is_ ending one (issue [#1095]). A transition into `occupied` from a status that held no party creates `/restaurants/{id}/visits/{visitId}` in the same commit as the state and the audit entry; a transition out of the party statuses stamps `closedAt`, `closedByUserId` and `closed` - or `abandoned`, when the caller says the party walked out - onto the visit it was pointing at. Two documents and a third, never one without the others, so a table occupied by nobody cannot exist. `moveTableVisit` in `restaurants/move-table-visit.ts` is the one operation that is not a single table's transition: it changes the visit's `tableId` and nothing else about it, occupies the destination, turns over the table the party left, and appends an audit entry for each - because closing and reopening would give the party a new visit id and lose the orders that hang from the old one.
- **Seating a table also confirms the guests who scanned it** (`RD-TS-2`). Since issue [#1101] the same commit reaches a fourth collection: `syncTableSessions` activates the table's `pending` sessions onto the visit it opens, and closes the visit's `active` sessions when it ends one. It is one equality-only query, run only on the two transitions that open or end a visit - most of a table's day is neither and pays nothing. Opening looks up by `tableId`, because a pending session has no visit to be found by; ending looks up by `visitId`, because a party that moved tables is at a different table from the one its sessions named. A pending session that went idle while it waited is written `expired` instead of activated, since somebody who scanned the sticker at lunch is not part of the party seated at dinner.
- A table has **at most one open visit**, and nothing checks it. `TableState.visitId` is the only pointer at an open visit: the commit that seats a table writes it and the commit that frees the table drops it, so a second visit at one table would take a second seating of a table that is already `occupied`, which fails its `expectedStatus` check against the one document both hosts contend on. Querying `visits` for the open one instead would be a second answer to a question the state already answers, free to disagree with it, and it would put a whole collection in the read set of every transition - a party seated at table 5 invalidating a transaction about table 12. `moveTableVisit` reads the same pointer on the **destination**, because the matrix alone does not refuse a destination that is mid-order: `ordering -> occupied` is legal, being a party sending the waiter away, so without the check a second party walked onto that table would overwrite the pointer and leave the first party's visit unreachable.
- Ending a visit lands the table on `cleaning` and never on `available`, even though the matrix allows `occupied -> available`. The matrix says what a _table_ may do and is right as it stands - that transition is the table wrongly seated and immediately corrected - but a real party ending must leave an explicit next action, or the table is offered to the next party with the last one's plates on it. The narrowing applies only while a visit is open, so a table that never had one is unaffected. `TABLE_STATUS_AFTER_VISIT` is that value in both copies of the model, and the parity spec compares them.
- The transition matrix is **copied** into this project, and the copy is checked. `restaurants/table-state.ts` repeats `TABLE_STATUSES` and `TABLE_STATE_TRANSITIONS` from `libs/bite-tribe-common/model`, which this project cannot import - `rootDir: src`, no path mappings, and a deploy that uploads `lib/` alone. `src/__specs__/table-state-parity.spec.ts` reads both files as text and compares the statuses, their order and every row, exactly as `role-list-parity.spec.ts` does for `BITE_TRIBE_ROLES`. A duplication nothing checks is one that drifts, and this one would drift silently: both copies would pass their own tests while the staff view offered a button the backend refuses. `restaurants/table-visit.ts` and `src/__specs__/table-visit-parity.spec.ts` repeat the arrangement for the visit statuses, the set that ends a visit and `TABLE_STATUS_AFTER_VISIT` (issue [#1095]).
- `shared/target-user.ts` resolves "the account being acted on" from a `uid` or an `email`, and `setUserRoles` and the two staff callables share it. Whoever grants a role was told an address, not a Firebase uid - an operator by the restaurant on the phone, a restaurant by the person in front of them.
- Automatic restaurant-candidate detection (`create-restaurant-candidate-on-bite-create.ts`) only fires for Bites without a verified `restaurantId`, requires at least `5` matching nearby unverified Bites within `200m`, skips creation when a nearby verified restaurant matches, updates a nearby pending candidate instead of duplicating, and never writes back to Bite documents. Reuse the shared clustering helpers in `utils/restaurant-candidate-store.ts` and `utils/restaurant-candidates.ts` rather than duplicating query, matching, or candidate-build logic across the manual callable and the trigger.
- Email verification callables must use Firebase Admin Auth as the source of truth and mirror only derived metadata to `/users/{uid}`. Manual resend requests are throttled for one hour. Automatic reminders run monthly at 10:00 Europe/Zurich, stop after three successful sends, and exclude accounts that have trusted Google or Apple provider links.
- Email verification delivery uses Firebase Admin verification links and the Google Workspace/Gmail API credentials from the functions runtime environment: `GOOGLE_WORKSPACE_CLIENT_EMAIL`, `GOOGLE_WORKSPACE_PRIVATE_KEY`, `GOOGLE_WORKSPACE_DELEGATED_USER`, and `GOOGLE_WORKSPACE_SENDER_ADDRESS`. All four are set through `apps/bite-tribe-firebase/set-workspace-secrets.sh`.
- The mail's visible sender is configuration of its own, never the delegated mailbox. `GOOGLE_WORKSPACE_DELEGATED_USER` says which Workspace account performs the Gmail API delegation and is infrastructure; `GOOGLE_WORKSPACE_SENDER_ADDRESS` says what a recipient sees, and `createRawEmail` builds `From: BiteTribe <sender>` from that one alone. Building `From` from the delegated user published a maintainer's personal mailbox to every user who requested a resend, and made the visible sender change whenever the delegation account changed; see issue [#1265]. A missing sender address throws rather than falling back to the delegated user, because a fallback would keep sending from the personal address with nothing to surface it. Gmail rewrites `From` to the authenticated mailbox unless the address is on the delegated mailbox's `Send mail as` list, or is that mailbox itself, so setting the secret is only half the configuration. Two Workspace settings are needed and they are not the same one: an Admin-console **alternate email address (alias)** makes `noreply@bitetribe.app` exist and receive, while the **`Send mail as`** entry under Gmail - Settings - Accounts and Import is what authorises sending as it. An alias does not reliably propagate into that list, and between 2026-08-09 and 2026-08-18 it had not, so a correct header was rewritten in transit and the shipped fix changed nothing a recipient saw. Verify the `Send mail as` list, not the alias, and verify it by a real send: the rewrite happens after the code under test has produced its header, so no spec can catch it. The subject of the console-owned Firebase Auth registration template is kept at the catalog's English wording, `Verify your BiteTribe email address`, so one operation does not present two subjects; that template is console configuration, not repository code. The one-word spelling settled in [Implementation - Store Listing Assets](store-listing-assets.md) moved that wording, so two console settings have to follow the catalog before the next functions deploy, or the two mails disagree again exactly as [issue-1265](../records/issue-1265.md) describes: the Firebase Auth template subject, and the `Send mail as` display name on the delegated mailbox, which must match `SENDER_NAME` or Gmail rewrites what the recipient sees. The registration mail's `bite-tribe.firebaseapp.com` action link stays for now: it is `authDomain`, which is also the Google and Apple OAuth redirect origin, so moving it is a Hosting, DNS, provider and app-config change sequenced after 1.0.1 rather than an RC-time edit.
- The verification mail is localized, not hardcoded English. Subject, body, and link label come from the `emailVerification.*` keys of the shared i18n catalog, and both senders - `resendEmailVerification` and the scheduled `sendEmailVerificationReminders` - resolve the recipient's language through `shared/utils/get-user-language.ts`, the same `settings/{uid}.language` read that push notifications use. An unknown or missing language falls back to English rather than blocking the send, because an account-security mail in the wrong language still beats none. Translated copy is MIME-encoded on the way out: the subject as an RFC 2047 encoded word when it leaves ASCII, the body as base64 with a matching `Content-Transfer-Encoding`, because the default 7-bit encoding would deliver anything non-English as mojibake. See issue [#1264].
- Display name uniqueness is backend-owned. `claimDisplayName` normalizes the name (trim + lowercase), then writes a `/displayNames/{normalizedName}` claim document inside a transaction so concurrent claims of the same normalized name cannot both succeed; the same transaction releases the caller's previous claim on rename and keeps `/users/{uid}.displayName` and `normalizedDisplayName` consistent. `checkDisplayNameAvailability` is a read-only advisory check that treats a name already owned by the caller as available. There is no display name backfill: both checks also scan `/users`, so a user who registered before claims existed is protected without one, and claims their own name when onboarding next runs. See [UC - Run Operational Migrations](../use-cases/uc-run-operational-migrations.md). Reuse `normalizeDisplayName`/`isValidNormalizedDisplayName` from `users/display-name-utils.ts` rather than re-implementing normalization. Emulator specs (`display-name-claims.emulator-spec.ts`) cover concurrent claims, rename/release, and the unclaimed legacy name.
- A collection-group query needs its single-field index exemption committed in `apps/bite-tribe-firebase/firestore.indexes.json`. Firestore indexes every scalar field at collection scope automatically, but never at collection-group scope, so a `collectionGroup(x).where(field, ...)` without an exemption compiles, passes the emulator, passes every unit test, and then fails in production with `FAILED_PRECONDITION`. The account-deletion cascade shipped that way and could not delete likes or anonymize BiteTrail sales; see issue [#1227]. `src/__specs__/firestore-collection-group-indexes.spec.ts` pairs every collection-group filter in the functions source with an exemption so the gap fails the build instead. Index changes deploy from CI, in the `deploy-firestore-indexes` job - `firebase deploy --only functions` never touches them. Keep the two deploys separate and run the index deploy first: the Firestore API builds an index in the background and the CLI returns without waiting for `READY`, so a function that needs a new index must not go live in the same step. That ordering is enforced rather than remembered: the index job deploys the specification and then runs `npm run firestore:assert-indexes-ready`, which polls until everything `firestore.indexes.json` declares is present and `READY`, and `deploy-functions` needs that job. A build large enough to outlast the wait fails the job rather than holding the deploy open; re-running it once the build finishes passes with no code change. Locally, the same deploy is `npm run deploy:indexes` from `apps/bite-tribe-firebase/functions`, or the `bite-tribe-firebase:firebase-deploy-indexes` Nx target that wraps it. Verify a deployed exemption under Firestore - Indexes - `Automatic` - Exemptions, in either console: `https://console.firebase.google.com/project/bite-tribe/firestore/databases/-default-/indexes/automatic?selectedTab=automatic` or `https://console.cloud.google.com/firestore/databases/-default-/indexes/automatic?project=bite-tribe`. The default `Manual` view lists only composite indexes, so an exemption looks missing until the `Automatic` toggle is selected. `firebase firestore:indexes --pretty` confirms an exemption exists but prints no build state for it. That is the CLI, not the resource: the Firestore Admin API reports `state` on every index inside a `Field`, verified against the live project on 17 September 2026, and `assert-firestore-indexes-ready.mjs` reads it there. The CLI is the wrong tool for the question, not the API.
- Account deletion is backend-owned. `deleteOwnAccount` proves the sign-in is recent from `request.auth.token.auth_time` (five minutes) rather than relying on Firebase's client-side recent-login rule, because the cascade runs with admin privileges; a stale token returns `failed-precondition`/`reauth_required` so the app can re-authenticate and retry. Progress is recorded in `/accountDeletions/{uid}` and an already completed job returns immediately, so a retried call is a no-op. Data is removed before the Firebase Auth account, never after, so a failure leaves a signed-in user who can retry rather than an unreachable data set. A deletion that keeps content alive must also refresh anything cached about the user: this one prunes `/meta/leaderboardDaily` and calls `rebuildLeaderboard`, because those snapshots hold display names and emails and are otherwise only rebuilt by a Bite create or delete. The per-category contract is in [UC - Use Account And Legal Flows](../use-cases/uc-use-account-and-legal-flows.md).

## Deploy

A push to `develop` deploys the functions. The `deploy-functions` job in
`.github/workflows/pipeline.yml` installs this package, runs the `predeploy`
lint and `tsc` from `apps/bite-tribe-firebase/firebase.json`, and runs
`firebase deploy --only functions` against `bite-tribe` under its own service
account. Nobody runs a command for a normal change, and the deployed revision
corresponds to the commit CI verified rather than to a workstation. Before
[issue #1464][#1464]
this was `npx nx run bite-tribe-firebase:firebase-deploy`, run by hand, which
is why a merged function could sit undeployed for as long as nobody remembered.

Four things stay outside that job on purpose.

- **Firestore indexes.** Deployed first, separately, and by hand, for the
  reason under the collection-group rule above. The job asserts they are there
  before it deploys anything.
- **Deleting a function.** Removing an export makes the CI deploy fail rather
  than take a live endpoint away, because the CLI runs `--non-interactive` and
  the deletion prompt becomes an error. Deploy the removal locally and
  deliberately.
- **Secret values.** `GOOGLE_GEOCODING_API_KEY` and the four
  `GOOGLE_WORKSPACE_*` secrets live in Secret Manager and bind at deploy time.
  CI triggers the binding and never sees a value, so a rotated secret needs no
  pipeline change. A binding that fails surfaces as a runtime send failure, not
  as a deploy error - after a deploy that touches the mail path, prove it with a
  real `resendEmailVerification` call rather than a green job.
- **Rollback.** Gen2 has none. Recovery from a bad deploy is a forward deploy of
  the reverted commit.

The local deploy remains the fallback for those cases and for an outage in the
pipeline:

```bash
npx nx run bite-tribe-firebase:firebase-deploy
```

## Validation

From `apps/bite-tribe-firebase/functions`:

```bash
npm run build
npm run lint
```

Use focused function tests when they exist for the changed callable or trigger.

### The Emulator Suite

`npm run test:emulator` runs every `*.emulator-spec.ts` against the Firestore
emulator from `firebase.emulator-test.json`; `npm run test:rules` runs the rules
spec alone. They are the only checks that exercise real documents, which is what
the token, display-name and candidate specs need - a mocked store asserts that
the code called `set`, which was never the part in doubt.

`jest.emulator.config.cjs` transforms one package inside `node_modules`.
`firebase-admin` reaches `jwks-rsa`, which imports `jose`, and jose 6 ships as
ESM only - so until issue [#1086] every emulator spec that loaded a module
importing `firebase-functions/https` failed to parse, and two of the four suites
could not run at all. Nothing here verifies an ID token; the specs hand a
handler its decoded `request.auth` directly. The dependency is on the import
path regardless, so it has to be loadable.

### `tsc` Is The Only Type Check

Neither the tests nor the linter compile this project.

- `jest.config.cjs` transforms through ts-jest against `tsconfig.dev.json`,
  which sets `isolatedModules`, so specs are transpiled per file and not
  type-checked. `tsconfig.dev.json` also `include`s only the spec files, and
  the build's `tsconfig.json` `exclude`s them, so the two configurations never
  meet over `src`.
- eslint reports style and rule violations, not assignability.

Confirmed rather than assumed: with
`const probeTypeError: number = 'definitely not a number';` appended to a source
file that a spec imports, `nx run functions:test` passed nine tests and
`nx run functions:lint` passed. Only `tsc` reported `error TS2322`.

That error used to reach `develop` green and surface in the `predeploy` hook of
`firebase.json`, at deploy time, on whoever's workstation ran the deploy. The
`functions-build` job in `pipeline.yml` now compiles them on every pull request,
which is what closes it.

The two jobs do not compile with the same compiler, and that is worth knowing
before trusting a green pull request. `functions-build` does not install this
package, so its `tsc` resolves to the workspace TypeScript 6; `deploy-functions`
installs it and compiles with the `^5.7.3` pinned here, which is also what a
workstation deploy uses. See [Current State - Nx And Dependency Migration Roadmap](../current-state/nx-and-dependency-migration-roadmap.md).

Rules:

- `functions-build` is the type check, not a formality. It exists because
  nothing else in CI compiles this project, so removing it removes the only
  compiler in the pipeline.
- A change to how the tests compile is not a substitute for it. If
  `isolatedModules` is ever removed from `tsconfig.dev.json`, the specs get
  checked, but the sources no spec imports still do not.
- Keep it building with `tsconfig.json`, the configuration the deploy actually
  uses. Compiling anything else would pass a build the `predeploy` hook then
  fails.
